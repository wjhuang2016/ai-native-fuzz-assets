# FLASHBACK DATABASE can reset recovered sequence values and reuse existing IDs

Status: remote `found_bug` id1500003; upstream [TiDB #69781](https://github.com/pingcap/tidb/issues/69781) filed with `found-by-ai` and `severity/major` after current-master RED/GREEN on authorized testbed `8220955`.

## User-visible symptom

After `FLASHBACK DATABASE`, a sequence inside the recovered database can start allocating from the beginning again. If a table in the same recovered database already contains rows generated by that sequence, the next sequence-backed insert can fail with a duplicate primary key.

This is not just display metadata drift. The recovered sequence returns values that were already materialized before the database was dropped.

## Minimal reproduction

```sql
DROP DATABASE IF EXISTS ai_native_seq_fb_20260713;
CREATE DATABASE ai_native_seq_fb_20260713;
USE ai_native_seq_fb_20260713;

CREATE SEQUENCE seq START WITH 1 INCREMENT BY 1 CACHE 100;
CREATE TABLE t (
  id BIGINT PRIMARY KEY DEFAULT NEXT VALUE FOR seq,
  note VARCHAR(64)
);

INSERT INTO t(note) VALUES ('before_1'), ('before_2');
SELECT * FROM t ORDER BY id;
SELECT NEXTVAL(seq) AS before_drop_nextval;

DROP DATABASE ai_native_seq_fb_20260713;
FLASHBACK DATABASE ai_native_seq_fb_20260713;
USE ai_native_seq_fb_20260713;

SELECT * FROM t ORDER BY id;
SELECT NEXTVAL(seq) AS after_flashback_nextval;
INSERT INTO t(note) VALUES ('after_flashback_default_insert');
```

Observed:

```text
before rows:            (1, before_1), (2, before_2)
before_drop_nextval:    3
after flashback rows:   (1, before_1), (2, before_2)
after_flashback_nextval: 1
INSERT default:         ERROR 1062 Duplicate entry '2' for key 't.PRIMARY'
```

## Controls

The same sequence/default path without recovery is healthy:

```text
two default rows: 1, 2
NEXTVAL(seq):    3
next default insert succeeds with id=4
```

An ordinary `AUTO_INCREMENT` table recovered by `FLASHBACK DATABASE` also avoids reusing `1` and `2`; the next insert succeeded with `id=30001` on this testbed. That isolates the failure to sequence runtime state, not generic schema recovery.

## Source proof

`FLASHBACK DATABASE` loads historical objects from snapshot meta:

- `pkg/ddl/schema.go:304-329` calls `snapMeta.ListTables` and appends a `RecoverTableInfo` for each `TableInfo`.
- `pkg/meta/meta.go:1425-1450` shows `ListTables` returns every `mTablePrefix` object; TiDB stores sequences as `TableInfo`.
- `pkg/ddl/schema.go:351-359` then calls `w.recoverTable` for every recovered object.

`recoverTable` recreates all objects through the ordinary table path:

- `pkg/ddl/table.go:292-300` calls `CreateTableAndSetAutoID`.
- `pkg/meta/meta.go:984-1008` restores row ID, auto increment, and auto random, but not sequence value or sequence cycle.

Sequence create/drop/runtime use a separate key:

- `pkg/ddl/sequence.go:70-80` calls `CreateSequenceAndSetSeqValue`.
- `pkg/meta/meta.go:1010-1017` writes `sequenceKey(tableInfo.ID)`.
- `pkg/meta/meta.go:1076-1088` deletes the sequence key during `DROP SEQUENCE`.
- `pkg/meta/autoid/autoid.go:1120-1172` reads `SequenceValue()` when allocating the next sequence cache.

So the failed proof obligation is:

```text
P: schema recovery has a historical TableInfo and valid GC/snapshot checks.
Q: generic table recovery restores all runtime state needed by that object.
F: sequence value/cycle state lives outside the generic AutoIDGroup and is not restored.
```

## Quality and dedup

This is distinct from the older sequence-default lazy-name-resolution family (`id30005` / sequence-default recover boundary). There the table default can point at a missing sequence because ordinary `CREATE TABLE ... DEFAULT NEXT VALUE FOR missing_seq` is already permissive.

Here the sequence object exists after `FLASHBACK DATABASE`; the bug is that its runtime value moves backward and reuses existing values.

It is also distinct from `id1500002` FK identity drift. The current root is special-object runtime state loss under `FLASHBACK DATABASE`, not foreign-key reference rebinding.
